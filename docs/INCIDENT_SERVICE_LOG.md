# Отчёт: устранение ошибки записи в `/var/log/service.log`

**Дата:** 2026-09-25  
**ВМ:** Ubuntu 24.04, `base-node01-tizrm` (`158.160.181.94`)  
**Сервис:** `service.service`, `/usr/local/bin/service`  
**Статус:** решено

## 1. Постановка проблемы

Сервис `service.service` должен был раз в секунду добавлять строку в
`/var/log/service.log`, но файл оставался пустым.

В журнале systemd наблюдалась повторяющаяся ошибка:

```text
Error: No permission to write to /var/log/service.log
```

Сервис при этом оставался запущенным, поэтому проблема не проявлялась как
падение unit-а.

## 2. Выполненные проверки

Диагностика выполнена по workflow Linux + Systemd проекта MCP-Linx:
проверены состояние unit-а, его конфигурация, пользователь запуска, путь и
атрибуты лог-файла, файловая система и журнал сервиса.

Ключевые результаты:

```text
ActiveState=active
SubState=running
MainPID=1467
User=service
Group=service
ExecStart=/usr/local/bin/service
```

Unit-файл не содержал ограничений `ProtectSystem`, `ReadOnlyPaths` или
`ReadWritePaths`, которые могли бы запрещать запись в `/var/log`.

Параметры файла до исправления:

```text
-rw-r--r-- service service /var/log/service.log
mode=644
uid=1003
gid=1003
```

Родительский каталог `/var/log` был доступен для записи, файловая система
смонтирована в режиме `rw`, свободное место присутствовало.

Однако `lsattr` показал:

```text
----i---------e------- /var/log/service.log
```

Флаг `i` означает `immutable`: даже владелец файла не может изменить его
содержимое до снятия атрибута.

## 3. Первопричина

На `/var/log/service.log` был установлен Linux-атрибут `immutable` (`i`).

Права `0644` и владелец `service:service` сами по себе были корректны, но
immutable-флаг действовал независимо от прав доступа и блокировал запись
процесса, запущенного от пользователя `service`.

## 4. Исправление

Снят только атрибут immutable:

```bash
sudo chattr -i /var/log/service.log
```

Изменения в `service.service`, права доступа и владелец файла не вносились.
Перезапуск сервиса не потребовался: процесс продолжил работу и повторял
операцию открытия файла каждые две секунды.

## 5. Верификация

### Проверка права записи

Проверка от имени пользователя сервиса завершилась успешно:

```bash
sudo -u service test -w /var/log/service.log
```

Результат:

```text
service_user_can_write=yes
```

### Проверка роста файла

До снятия атрибута размер файла был `0` байт. После исправления тот же
процесс увеличил его до `26` байт, затем до `91` байта. Файл содержал
строки:

```text
I am running
```

Количество строк продолжало увеличиваться.

### Проверка systemd

```text
ActiveState=active
SubState=running
MainPID=1467
NRestarts=0
```

PID процесса не изменился, поэтому успешная запись подтверждена именно тем
экземпляром сервиса, который был запущен через `service.service`.

### Проверка журнала и атрибутов

После исправления новых сообщений
`Error: No permission to write to /var/log/service.log` не обнаружено.
Атрибут файла изменился с `----i---------e-------` на
`--------------e-------`.

## 6. Изменённые объекты

На удалённой ВМ изменён только атрибут файла:

```text
/var/log/service.log
```

Файлы проекта и runtime-код MCP-Linx не изменялись. Пароль SSH в отчёт не
включается.

## 7. Рекомендации по предотвращению

При диагностике аналогичных сбоев проверять одновременно:

1. `systemctl show` и фактическое состояние unit-а;
2. владельца, группу и режим лог-файла;
3. `lsattr -d` на файл и его родительский каталог;
4. доступность через `runuser -u <service-user> test -w`;
5. ошибки процесса в `journalctl -u <unit>`.

При обнаружении `immutable` следует сначала установить источник атрибута и
только затем снимать его, если это соответствует политике эксплуатации.


## 8. Инструмент MCP-Linx

Для повторяемой диагностики добавлен read-only инструмент
`linux_file_diagnostics`. Пример вызова для данного инцидента:

```json
{
  "name": "linux_file_diagnostics",
  "arguments": {
    "path": "/var/log/service.log",
    "unit": "service.service"
  }
}
```

Инструмент проверяет `stat`, цепочку каталогов `namei`, атрибуты `lsattr`,
mount/space, свойства systemd-юнита и наличие `immutable`. Проверка
`test -w` от пользователя `service` включается отдельно:

```yaml
plugins:
  linux:
    privileged_tools: true
```

MCP-Linx не выполняет `chattr` автоматически: исправление атрибута остаётся
явным административным действием.
